# ICAN 无人仓仿真决策平台开发方案

> 文档用途：将现有网站原型落实为可在两人团队内交付的 MVP（最小可用版本）开发计划。  
> 结论：项目应定位为“无人仓仿真决策平台”，而不是若干独立的数据大屏。

## 1. 原型解读与产品定位

现有原型覆盖了完整的业务闭环：用户提出需求并上传资料，系统生成或编辑仓库场景，进行 AGV 仿真，发现异常，优化方案，并输出结果报告。

```text
自然语言需求 / 上传订单与配置
  → 需求结构化与模板选型
  → 仓库场景生成、编辑与校验
  → 任务分配与 AGV 仿真
  → 异常检测、指标统计
  → 参数优化与二次仿真
  → 优化前后对比、报告导出
```

原型页面与实际系统能力对应如下：

| 原型图 | 页面 | MVP 必须实现的能力 | 优先级 |
| --- | --- | --- | --- |
| image01 | 首页 / 任务创建 | 需求输入、文件上传、模板选择、创建项目 | P0 |
| image07 | 场景编辑器 | 二维仓库布局展示、组件放置/属性编辑、保存 | P0 |
| image02 | 仿真空间 | AGV 移动、控制按钮、日志、异常和实时指标 | P0 |
| image06 | 任务编排 / 智能体协同 | 工作流、任务队列、策略参数、智能体状态 | P1 |
| image05 | 方案进化 | 问题诊断、优化动作、版本与前后指标对比 | P0 |
| image04 | 运行报告 / 数据洞察 | 历史运行指标、趋势和异常统计 | P1 |
| image03 | 资源中心 | 场景/策略模板的浏览与套用 | P2（可先静态） |

### MVP 演示主线（必须跑通）

```text
选择“电商中型仓”模板
→ 输入需求并生成项目
→ 查看或微调二维仓库场景
→ 启动 10 台 AGV 执行 20 个订单
→ 注入“道路封闭”或“低电量”异常
→ 系统发现拥堵 / 延迟问题
→ 自动生成一个优化方案并再次仿真
→ 在进化报告中展示改善结果并导出 PDF
```

资源交易、复杂权限、真实 CAD 解析、完整 3D、ROS/Gazebo、强化学习与自训练大模型均不进入首版。它们会显著提高风险，却不会增强演示闭环。

## 2. 对初步方案的评估与调整

现有方案的核心判断是合理的：前后端分离、二维离散事件仿真、算法智能体优先于大模型、通过固定 JSON 协议协作。这些应保留。

建议做以下收敛：

| 初步方案 | 建议 | 原因 |
| --- | --- | --- |
| Next.js + React | 保留；若只做纯前端展示，也可用 Vite + React | Next.js 适合路由和后续部署；两人无需同时引入 SSR 复杂度 |
| PostgreSQL + Redis + Celery | 第 1 个可运行版本先使用 SQLite + FastAPI 后台任务；第 2 阶段再接 PostgreSQL/Redis | 仿真、优化和报告是核心，基础设施不能抢占首周时间 |
| SimPy + NetworkX + A* | 保留 | 足以完成二维多 AGV、路径、冲突、充电和指标演示 |
| Optuna / OR-Tools | 先实现规则调参或小范围枚举；Optuna 作为增强项 | 首版重点是得到稳定、可解释的优化前后差异 |
| 大模型智能体 | 采用“规则解析 + 表单兜底”，大模型仅做可选增强 | 断网或模型调用失败时仍可完整演示 |
| React-Konva 编辑器 | 首版先做“模板加载 + 属性修改 + 关键组件拖动”，再补撤销/框选等高级编辑 | 避免编辑器占据过多开发时间 |
| 报告导出 | 首版只保证 PDF；PPT/视频/ZIP 放入增强项 | PDF 最符合答辩交付需求 |

**架构原则：** 逻辑上拆分 `web`、`api`、`simulation`，部署上保持一个仓库、一个后端服务即可；不要一开始做微服务。

## 3. 推荐技术方案

### 3.1 前端（负责人 A）

| 目标 | 技术 | 用途 |
| --- | --- | --- |
| 框架 | Next.js / React / TypeScript | 页面路由、组件开发、类型约束 |
| UI | Ant Design | 表单、上传、表格、抽屉、消息提示 |
| 画布 | React-Konva | 二维仓库、AGV、路径、热区的绘制与交互 |
| 图表 | ECharts | 指标卡、趋势图、优化前后对比 |
| 流程图 | React Flow | 智能体协同和任务编排流程 |
| 状态与请求 | Zustand + TanStack Query | 前端状态和接口缓存 |
| 实时通信 | 原生 WebSocket | 接收仿真 tick、事件和日志 |
| 测试 | Vitest（关键组件） | 保证数据转换和核心交互 |

### 3.2 后端与仿真（负责人 B）

| 目标 | 技术 | 用途 |
| --- | --- | --- |
| API | FastAPI + Pydantic | REST、WebSocket、数据校验、自动 Swagger |
| 持久化 | SQLAlchemy；SQLite 起步，PostgreSQL 交付前切换 | 项目、场景、运行、报告元数据 |
| 文件处理 | pandas + openpyxl + PyYAML | 订单 Excel、JSON/YAML 配置导入 |
| 仿真 | SimPy | 离散事件、任务队列、时间推进 |
| 图与路径 | NetworkX + A* | 地图图结构、最短路和重规划 |
| 数据分析 | NumPy + pandas | 指标、报告数据和对比 |
| 优化 | 规则搜索 / 参数枚举；后续可接 Optuna | 产生可解释的进化方案 |
| 报告 | Jinja2 HTML + Playwright/Chromium PDF | 导出可打印的方案报告 |
| 测试与部署 | pytest + Docker Compose | 仿真单测与统一运行环境 |

### 3.3 “智能体”的正确实现

首版的智能体是职责清晰的算法模块，不应让 LLM 直接控制每一步 AGV：

- 调度智能体：选择可执行任务的 AGV（优先级、距离、电量、负载）。
- 导航智能体：A* 规划、道路封闭后的重规划。
- 能源智能体：低电量预警、充电桩选择和充电调度。
- 安全智能体：节点冲突、道路占用、拥堵和死锁风险。
- 评估智能体：完成率、平均时长、拥堵次数、空驶率、能耗。

自然语言功能采用“关键词/规则解析 → 表单确认 → 可选 LLM 增强”三层设计。用户输入无法可靠解析时，界面要求补充结构化字段，而不是让系统猜测。

## 5. 代码目录与所有权

建议在当前代码目录建立如下结构：

```text
A Factory Built with a Single Word/
├─ apps/
│  └─ web/                 # A 拥有
├─ services/
│  ├─ api/                 # B 拥有
│  └─ simulation/          # B 拥有
├─ packages/
│  ├─ contracts/           # 双方共同维护，需评审
│  └─ mock-data/           # A 主维护，B 可引用
├─ scenarios/              # B 主维护
├─ reports/                # B 主维护，A 负责视觉模板建议
├─ docs/
├─ docker-compose.yml      # 共同维护，B 主合并
└─ README.md               # 共同维护
```

- A 不修改 `services/` 的业务实现；B 不修改 `apps/web/` 的页面实现。
- A 用 `packages/mock-data` 完成页面和动画，不等待接口完成。
- B 用 Swagger、pytest 和 WebSocket 客户端完成接口和仿真验证，不等待页面完成。
- 只有协议、启动说明和 Docker 文件属于交叉区域；修改前先同步。

## 6. 六周开发阶段与两人分工

> 总原则：每一阶段都必须交付“页面可访问、数据可追溯、失败可恢复、测试可验证”的闭环。禁止仅新增页面、DTO 或 Mock 函数而不接入路由、业务 ID 和实际页面调用；Mock 与真实 API 的切换必须按模块进行，不能一次性关闭全局 Mock。

| 阶段 / 时间 | 阶段目标 | 负责人 A：前端与交互 | 负责人 B：后端与仿真 | 阶段验收 |
| --- | --- | --- | --- | --- |
| 0：第 1–2 天 | 定范围、冻结协议 | 梳理“登录→首页→项目→场景→仿真→报告”的主路径；定义加载、空状态、错误状态和 Mock 数据 | 定义用户、项目、场景、仿真运行、通知的实体与 API；冻结 WebSocket 消息结构 | `contracts`、OpenAPI 初稿和端到端演示脚本通过共同评审 |
| 1：第 1 周 | 前端入口闭环与后端契约冻结 | 注册登录、账户、搜索、通知全部路由；接入 `RequireAuth`、登录回跳、演示账号、头像和密码 Mock；补齐加载/空/失败状态；为用户角色做页面级可见性控制 | 固化真实 Pydantic/OpenAPI 响应；提供 `/health`、模板、项目、场景 API；明确本周不提供的认证、搜索、通知接口，并写入契约 | 所有新增页面均可访问；未登录不能进业务页；前端 DTO 与后端响应样例逐字段一致；路由守卫、登录和密码修改有测试 |
| 2：第 2 周 | 项目—场景真实创建闭环 | 首页调用“创建项目 → 创建场景 → 写入 projectId/scenarioId → 跳转编辑器”；模板卡使用真实模板数据并套用布局；创建失败可恢复且按钮可重试 | 实现项目、模板详情/套用、场景创建接口；项目返回字段与 DTO 对齐；为模板场景提供可直接保存的 `data` | 从首页创建或套用模板后，编辑器收到正确 `projectId/scenarioId`，刷新后仍能加载同一场景；失败时不遗留“生成中”状态 |
| 3：第 3 周 | 场景编辑真实读写与项目上下文 | 编辑器从 URL 优先、Store 兜底读取 ID；加载场景、保存场景、显示保存/冲突/失败状态；将组件数组与后端 `Scenario.data` 通过 Mapper 双向转换 | 场景查询、保存、校验、自动布局与版本接口；返回统一的场景数据结构；增加边界、重叠和 schema 校验 | 编辑器修改后刷新一致；任意无效或缺失 ID 有清晰空状态；前后端各有场景 Mapper/接口测试 |
| 4：第 4 周 | 仿真运行与实时数据闭环 | 编辑器创建仿真并保存 `simulationId`；仿真页从 URL/Store 读取 ID；控制开始/暂停/停止、异常注入；用 `useSimulationStream` 连接 WebSocket 并更新画布、指标、事件 | 创建/查询/控制/异常注入接口；WebSocket tick、事件和完成消息；补充事件历史或明确只通过 WS 获取；SimPy、路径、充电和拥堵 MVP | 不使用 `mock` 作为真实 ID；10 AGV/20 订单可运行；断线重连后页面恢复；异常注入同步产生事件与指标 |
| 5：第 5 周 | 进化、报告与账号真实能力 | 使用 `simulationId` 创建进化并保存 `evolutionId`；展示真实诊断和优化前后指标；真实 PDF 下载；把账户、搜索、通知由 Mock 按模块切换到真实接口，补齐角色禁用/无权限状态 | 进化创建/查询、报告 PDF、用户资料/密码/偏好、搜索、通知、成员角色权限接口；返回模型与前端 Mapper 对齐 | 指定仿真可生成并查看进化结果和 PDF；搜索/通知关联到具体 ID；viewer 无法编辑和启动仿真 |
| 6：第 6 周 | 集成稳定性、降级与交付 | 全量验收从登录到导出；Mock/真实模式可分别启动；为网络失败、接口 401/403/404、WS 断线、空项目提供可操作提示；1920×1080 演示适配与录屏 | OpenAPI 契约测试、pytest、数据库迁移、Docker Compose、一键启动、固定随机种子、通知持久化和审计日志 | 连续 20 次端到端演示稳定；前端真实 API、WS 与后端测试全部通过；断网时可切回本地演示数据 |

### 6.1 第 1 周前端任务清单

第 1 周的目标不是完成企业级权限服务，而是完成可验证的前端入口闭环，并冻结项目、模板、场景的真实接口边界。账号、搜索和通知可暂时使用 Mock；项目、模板和场景必须至少有一条真实接口联调路径。不得出现“页面已建但路由未注册”“ID 已保存但业务页未消费”“DTO 已创建但与 Pydantic 不一致”的情况。

| 模块 | 第 1 周前端任务 | 应预留的接口/状态 | 验收标准 |
| --- | --- | --- | --- |
| 登录与鉴权 | 新增 `/login`；账号、密码、记住登录状态、演示账号快捷填充、登录失败提示；新增 `/forgot-password` 占位入口 | `authApi.login/logout/getMe`；`useAuthStore`；token、当前用户、登录状态 | 使用演示账号 `admin / ican2026` 可登录；登录后回跳原目标页面 |
| 路由守卫 | 为编辑器、仿真、进化、报告、资源等业务路由添加 `RequireAuth`；未登录自动跳转登录页 | `redirectTo` 参数；鉴权加载态与无权限态 | 未登录直接输入业务 URL 不可进入；退出后访问业务页会被拦截 |
| 账号中心 | 新增 `/account/profile`、`/account/settings`、`/account/preferences`；资料编辑表单、修改密码弹窗、头像与角色展示 | `User`、`UserProfile`、`UserPreference` 类型；资料/密码/偏好 API 占位 | 顶栏菜单可进入各页；资料和偏好修改在 Mock 模式下可即时生效 |
| 顶栏账号菜单 | 完善“个人中心、账号设置、退出登录”；在顶栏显示当前用户头像、昵称、角色 | 用户全局状态；退出后清理本地状态 | 所有业务页均显示一致的账号入口与退出行为 |
| 全局搜索 | 顶栏搜索建议；新增 `/search?q=`；按项目、场景、报告、模板分类呈现；空结果/加载/清空状态 | `searchApi.search(keyword)`；`SearchResult` 含 type、title、description、targetUrl | 输入关键词有建议；点击结果可跳到正确页面 |
| 消息与通知 | 顶栏铃铛未读角标、通知抽屉、新增 `/notifications`；支持全部/未读/告警/系统筛选、单条已读、全部已读和跳转 | `Notification` 含 id、type、title、content、read、createdAt、targetUrl | 可查看、标记已读和跳转 Mock 通知；未读数同步更新 |
| 设计与通用状态 | 统一登录页、业务布局、面包屑、卡片、表单、抽屉、空状态、错误状态、断网状态；确保 1920×1080 主展示适配 | 通用 `PageState`、`EmptyState`、`ErrorState` 组件 | 页面视觉一致；请求加载、无数据和失败时无空白页 |
| 测试与文档 | 为路由守卫、登录状态、搜索跳转、通知已读添加单测；更新前端启动与演示说明 | 测试 Mock、演示账号说明 | 第 1 周演示路径可稳定复现，关键交互有自动化验证 |

### 6.2 第 1 周前端演示闭环

```text
打开登录页
→ 使用演示账号登录
→ 进入首页并查看账号菜单
→ 搜索一个项目并跳转
→ 查看通知、标记已读并跳转到关联页面
→ 打开个人中心修改昵称或通知偏好
→ 退出登录
→ 再访问仿真页，被正确拦截回登录页
```

### 每个阶段的协作方式

1. 阶段开始：双方共同确认协议样例和验收条件（不超过 30 分钟）。
2. 阶段中：A 对 Mock 协议编写页面；B 对同一协议编写 API 与测试。
3. 阶段末：先把 A 的数据源从 Mock 切到真实 API/WS，再做一次端到端回归。
4. 每天固定 15 分钟同步：已完成、协议变更、阻塞项、明日目标。

## 7. Git 协作规范

```text
main                     可演示的稳定版本
develop                  阶段集成分支
feat/web-home            A
feat/web-editor          A
feat/web-simulation      A
feat/api-project         B
feat/api-scenario        B
```

- 不直接向 `main` 或 `develop` 推送。
- 一个功能分支只解决一个清晰的需求；提交信息使用 `feat:`、`fix:`、`docs:`、`test:`。
- 合并前由另一人检查：是否修改越界目录、是否变更协议、是否有测试或可复现演示步骤。
- 每周至少一次从 `develop` 同步到自己的分支，尽早解决冲突。

## 8. 最先要做的技术验证

不要先平铺七个页面。第一个可运行里程碑应在第 1 周末或第 2 周初完成：

```text
读取固定仓库场景
→ 后端创建 10 台 AGV 与 20 个订单
→ A* 得到路径，仿真每秒推送状态
→ 前端画布显示 AGV 移动
→ 页面显示完成率、平均时长与拥堵次数
```

这条链路跑通后，再依次增加：场景编辑、异常注入、优化进化、自然语言增强与报告。这样能确保项目始终是可演示的真实系统，而非只有静态原型的界面集合。

## 9. 首版完成标准

以下全部满足即可称为 MVP 完成：

- 可从模板创建项目，支持自然语言描述和订单文件上传。
- 可查看并修改二维场景，且场景可保存、可再次加载。
- 可运行多 AGV 仿真，至少包含任务分配、路径规划、电量与一种冲突处理。
- 可注入至少两种异常（推荐道路封闭、低电量或订单激增）。
- 可生成诊断结果，运行至少两轮方案并展示优化前后指标。
- 可导出一份 PDF 报告。
- 在一台演示电脑上可通过 Docker 或一键脚本稳定启动；外部模型或网络不可用时仍能完成演示。
